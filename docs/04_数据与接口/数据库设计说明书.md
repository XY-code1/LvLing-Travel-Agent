## 3. 知识库模块（★ 完全本地向量库，不依赖 Dify）

> 🧭 **架构说明**：本项目知识库为**本地实现**——文档原件存本地磁盘、分块与向量存 MySQL、检索在后端内存做余弦相似度。这直接对齐比赛规则"需构建**本地**景区知识库"。唯一的外部依赖是"文本→向量"的 embedding 计算，通过 `ai_service_config` 的 `EMBEDDING` 类型配置（可指向本地部署的 embedding 服务）。

### 3.1 `kb_document` 知识库文档（原件 + 解析状态）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK AI | 主键 |
| `scenic_id` | bigint | NULL, IDX | 所属景区 |
| `file_name` | varchar(255) | NOT NULL | 原始文件名 |
| `file_type` | varchar(20) | NOT NULL | pdf/word/txt/md/excel/image |
| `file_path` | varchar(500) | NOT NULL | 本地存储路径（原件） |
| `file_size` | bigint | NULL | 字节数 |
| `char_count` | int | NULL | 解析出的字符总数 |
| `chunk_count` | int | NOT NULL DEFAULT 0 | 已生成分块数（与 `kb_chunk` 对应） |
| `parse_status` | tinyint | NOT NULL DEFAULT 0 | 0待解析 1解析中 2解析成功 3解析失败 |
| `embed_status` | tinyint | NOT NULL DEFAULT 0 | 0待向量化 1向量化中 2成功 3失败 |
| `fail_msg` | varchar(500) | NULL | 解析/向量化失败原因 |
| `status` | tinyint | NOT NULL DEFAULT 1 | 1=启用 0=停用（停用则不参与检索） |
| 公共字段 | | | 见 0.2 |

> ⛔ **红线**：⛔ 禁止出现任何 `dify_*` 字段或对 Dify/外部 RAG 平台的引用。文档解析（PDF/Word/Excel→文本）、分块、向量化全部在本系统后端完成。

### 3.2 `kb_chunk` 知识库分块 + 向量（★ 本地向量库核心表）

> 每个文档解析后按语义/长度切分为多个 chunk，每个 chunk 算出一个向量存本表。检索时把 chunk 向量载入内存做余弦相似度召回。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK AI | 主键 |
| `doc_id` | bigint | NOT NULL, IDX | 所属文档 `kb_document.id` |
| `scenic_id` | bigint | NULL, IDX | 所属景区（冗余，检索按景区过滤） |
| `spot_id` | bigint | NULL, IDX | 关联景点（若该 chunk 明确属于某景点，供溯源与视觉映射） |
| `chunk_index` | int | NOT NULL | 在文档内的顺序号（从 0 开始） |
| `content` | mediumtext | NOT NULL | 分块正文（送入 LLM 的上下文原文） |
| `title_path` | varchar(500) | NULL | 该块所属标题层级（如"核心景点特色详解>灵山大佛"），供溯源展示 |
| `token_count` | int | NULL | 该块估算 token 数 |
| `embedding` | mediumtext | NULL | 向量，JSON 数组字符串（如 `[0.013,-0.221,...]`），维度见 `embed_dim` |
| `embed_dim` | int | NULL | 向量维度（如 1024），与生成它的 embedding 模型一致 |
| `embed_model` | varchar(100) | NULL | 生成该向量的模型名（换模型需重建向量，用它识别） |
| `source_name` | varchar(255) | NULL | 来源展示名（默认取文档名，供答案溯源） |
| `status` | tinyint | NOT NULL DEFAULT 1 | 1=有效 0=失效 |
| `create_time` | datetime | NOT NULL DEFAULT CURRENT_TIMESTAMP | 创建时间 |

> ⛔ **红线**：
> - `embedding` 用 `mediumtext` 存 JSON 数组（MySQL 8.0 无原生向量类型，本项目在应用层做余弦计算，不用向量数据库，保持"本地、可复现、零额外中间件"）。
> - 换 embedding 模型后，旧向量维度不兼容，必须整库重算（按 `embed_model` 识别 + 重建），⛔ 禁止混用不同模型/维度的向量做相似度比较。
> - 索引：`idx_doc(doc_id)`、`idx_scenic(scenic_id)`、`idx_spot(spot_id)`。

## 4. AI 服务配置模块

### 4.1 `ai_service_config` AI 服务配置（★ 核心表）

> 所有外部 AI 服务的接入参数**集中存此表**，由管理员在后台"AI 服务配置"页可视化录入，⛔ 禁止任何硬编码。
>
> 🧭 **为什么要有凭证三件套字段**：不同服务的认证方式不同——LLM/Dify 用**单 token**（`api_key`）；阿里云 ASR/TTS/数字人用**三件套**（`AccessKeyId` + `AccessKeySecret` + `appKey`/`appId`）。单一 `api_key` 字段装不下阿里云凭证，故本表用通用凭证字段 + `extra_config` JSON 覆盖所有服务。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigint | PK AI | 主键 |
| `service_type` | varchar(30) | NOT NULL, IDX | 服务类型：LLM / VISION / ASR / TTS / KB / AVATAR |
| `provider` | varchar(50) | NOT NULL | 服务商名称（如 `阿里云`、`DeepSeek`、`Dify`） |
| `protocol` | varchar(30) | NULL | 协议：OPENAI_COMPATIBLE / ANTHROPIC_COMPATIBLE（仅 LLM/VISION 用） |
| `base_url` | varchar(255) | NULL | 接口地址 / Endpoint |
| `api_key` | varchar(1000) | NULL | 单 token 凭证（LLM/VISION/KB 用）⛔ 加密存储 ⛔ 不明文返回 |
| `access_key_id` | varchar(500) | NULL | 阿里云 AccessKeyId（ASR/TTS/AVATAR 用）⛔ 加密 |
| `access_key_secret` | varchar(1000) | NULL | 阿里云 AccessKeySecret ⛔ 加密 ⛔ 永不返回前端（连脱敏都不返回，只返回是否已配置） |
| `app_key` | varchar(255) | NULL | 阿里云智能语音 appKey / 数字人 appId |
| `region` | varchar(50) | NULL | 服务区域（如 `cn-shanghai`），阿里云系必填 |

| `dataset_id` | varchar(100) | NULL | Dify 知识库 datasetId（KB 用） |

| `timeout_ms` | int | NOT NULL DEFAULT 10000 | 超时毫秒 |
| `retry_count` | int | NOT NULL DEFAULT 1 | 重试次数 |
| `capability_verified` | tinyint | NOT NULL DEFAULT 0 | 连通性/能力校验结果 1通过 0未通过 |
| `verified_time` | datetime | NULL | 最近一次校验通过时间 |

| `remark` | varchar(255) | NULL | 备注 |

> ⛔ **红线**：
> - `api_key` / `access_key_id` 返回前端时脱敏为 `****1234`（保留后 4 位）；`access_key_secret` **连脱敏值都不返回**，前端只收到 `hasSecret: true/false`。

## 9. 建表交付红线

> 表清单见 **§0.4（18 张，全文唯一权威清单）**，此处不再重复列表，避免两处清单漂移。

⛔ **红线**：
- §0.4 的 18 张表 + 正文 §1~§8 的字段定义为唯一标准。Codex **不得新增未列出的表、不得删除表、不得修改字段名/类型/长度**。
- 若开发中确需新表或新字段，**必须停止并回问**，由架构方裁定后更新本文档，严禁自行建表、自行加字段。
- 所有建表脚本统一放 `database/schema.sql`，初始化数据（含内置 admin 账号、示范景区基础数据、演示开关初值）放 `database/data.sql`。
- `schema.sql` 建表顺序须满足外键/引用先后：先 `sys_admin`、`scenic`，再 `spot`/`route`，再 `route_spot` 等关联表。
- 交付自检：建库后表数量必须 **等于 18**，`SHOW TABLES;` 结果与 §0.4 逐一比对，缺表或多表即为不通过。
